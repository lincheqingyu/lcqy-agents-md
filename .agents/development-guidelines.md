# 通用开发规范

适用范围：需要修改代码、配置或项目文档的项目。

## 工程原则

- 优先选择长期可维护、能降低未来开发成本的方案，避免没有明确收益的技术债。
- 先阅读现有代码、配置和文档，优先复用已有的可扩展实现。
- 保持单一真相源。类型、配置、写入口和派生文档应各有明确的权威来源。
- 优先使用简单、清晰、符合项目现有约定的结构，避免为假设中的需求增加抽象。
- 修复问题前确认可观察的失败行为、调用链和受影响的边界。
- 结构性问题通过重构解决，不用特例、临时补丁或过度兜底掩盖根因。
- 只实现当前需求和已验证的约束，与当前任务无关的重构、依赖升级和基础设施改造应单独提出。
- 删除被替代、无效和不再需要的代码，避免保留两套实现。

## 变更流程

- 开始前阅读项目说明、相关代码、构建配置、测试入口和 CI 配置。
- 将需求转换为可验证的结果，确认假设、边界和可能受影响的调用方。
- 优先设计最小可行的变更，保持代码在修改过程中可编译或可运行。
- 变更造成的废弃导入、变量、函数和文件应一并清理，但不要借机删除与任务无关的既有内容。
- 完成后复查变更范围、错误处理、兼容性、资源生命周期和职责边界。

## 测试与验证

- 测试面向用户可观察的行为、持久化状态和项目负责的契约，不绑定偶然的实现细节。
- 行为变化和 Bug 修复应增加或更新回归测试。Bug 修复应先有能复现问题的失败测试，再实现修复。
- 优先使用真实的下一层依赖和真实资源验证关键路径，只在边界依赖不可控或成本不合理时使用 mock。
- 先运行能覆盖本次变更的最小相关检查；变更跨越共享子系统、CI 要求或准备发布时，再扩大验证范围。
- 使用项目声明的 formatter、静态分析、类型检查、测试和构建入口，不为了通过检查而削弱检查。

## 文档与信息职责

- 文档说明目的、入口、约束和决策背景，不重复维护代码已经表达的实现逻辑。
- 每条信息只有一个权威来源，其他文档使用链接、索引或生成方式引用它。
- 文档应靠近它描述的模块，仓库级 README 负责导航，不承担所有细节。
- 代码、目录、命令或契约发生变化时，检查相关文档和索引是否仍然准确。
