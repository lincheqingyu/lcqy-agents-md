# 技术栈开发规范

按项目实际使用的技术栈选择对应章节，只复制适用章节到目标项目的 `AGENTS.md` 或技术文档中。

## Java

- 以项目声明的 Java 版本、source/target 兼容级别、构建工具、wrapper 和锁定文件为事实源。
- 使用项目提供的 JDK 和构建入口，不未经授权升级 JDK、插件或依赖。
- 保持既有 package/module 边界和依赖方向，业务规则放在负责该规则的层中。
- 除非明确要求破坏性变更，保持公开 API、序列化格式、持久化 schema、事务边界和错误语义兼容。
- 使用 try-with-resources 管理可关闭资源；为执行器、队列、连接池和重试设置明确上限。
- 在负责失败语义的边界处理异常，保留原始 cause，不静默返回成功值或降级结果，不记录密钥和敏感载荷。
- 遵循项目已有的 formatter、编译器告警、静态分析和测试约定。

## Python

- 使用项目声明的 `pyproject.toml` 和 `uv` 工作流，优先通过 `uv sync` 解析和同步环境。
- 除非项目明确要求，不引入 `pip` 虚拟环境、Poetry 或独立的 `requirements.txt` 作为第二套依赖入口。
- 使用明确的类型模型和类型提示，避免用松散的 `dict` 或字符串表示稳定的领域数据。
- 遵循项目现有的 formatter、lint、类型检查、测试和打包入口。

## TypeScript 与 React

- 不使用 `any` 隐藏不明确的数据形状，优先建立真实类型和明确的边界转换。
- 避免无依据的类型断言，优先通过运行时校验、类型收窄和现有类型定义表达事实。
- 假设使用现代浏览器，不为不需要的旧环境增加 polyfill 或兼容层。
- 保持组件小巧、专注且可复用，优先使用组合和清晰的数据流，避免重复状态和属性堆积。
- 优先复用项目已有的设计系统、基础组件和样式模式；没有设计系统时再建立共享 token 和可访问的基础组件。
- 遵循项目现有的包管理器、formatter、lint、类型检查、测试和构建入口。

## Rust 与 React/TypeScript

- Rust 是共享 API、领域模型和序列化契约的事实来源。
- 使用 `ts-rs` 或项目已有的生成流程产生 TypeScript 绑定，不手工维护与 Rust 重复的接口类型。
- 先确认生成入口、生成文件边界和 CI 校验方式，再修改共享契约。
- 保持 Rust 的错误语义、资源生命周期和前端可观察行为一致，并为契约变化补充跨边界测试。
